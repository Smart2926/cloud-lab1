## Яку проблему це розв'язує

Іноді клієнт може не отримати відповідь від сервера через проблеми з інтернетом або перевищення часу очікування.
У такому випадку користувач може повторити запит, хоча перший уже був виконаний.

Без ідемпотентності повторний запит може створити дві однакові пісні.

Використання Idempotency-Key дозволяє серверу розпізнати повторний запит і повернути результат першого виконання без створення дубліката.

## Поєднання із завданням №6
У завданні №6 було реалізовано асинхронну обробку через Azure Service Bus.

Після отримання запиту API створює завдання, надсилає повідомлення в чергу та повертає клієнту 202 Accepted.

Окремий контейнер Worker отримує повідомлення з черги та створює пісню в PostgreSQL.

Ідемпотентність доповнює цю систему.

Якщо клієнт повторно надсилає запит із тим самим Idempotency-Key, API повертає попередню відповідь і не надсилає нове повідомлення в чергу.

Крім того, Worker перевіряє стан завдання перед обробкою. Якщо повідомлення з тим самим job_id надійде повторно, вже виконане завдання не призведе до створення другої пісні.

Таким чином, Idempotency-Key захищає від повторних запитів клієнта, а перевірка у Worker — від повторної обробки повідомлень із черги.

Актуальний результат виконання клієнт може перевірити через GET /jobs/{job_id}.
