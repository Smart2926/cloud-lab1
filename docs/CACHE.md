# Кешування операцій читання

Для зменшення часу відповіді REST API було налаштовано кешування списку пісень за допомогою Azure Managed Redis.

Для перевірки ефективності кешування проведено два навантажувальні тести за допомогою k6: без кешу та з увімкненим Redis.

## Порівняння результатів

Обидва тести проводилися з однаковим навантаженням: 20 віртуальних користувачів протягом 10 хвилин.

За результатами тестування отримано:

| Показник | Без кешу | З кешем |
|---|---:|---:|
| Латентність p95 | 3149,07 мс | 2550,82 мс |
| Кількість запитів за секунду (RPS) | 16,41 | 21,51 |
| Завантаження CPU PostgreSQL | 20,81% | 20,20% |
| Read IOPS PostgreSQL | 0,10 | 0,00 |

Після ввімкнення Redis латентність p95 зменшилася приблизно на 19%.

Кількість оброблених запитів за секунду збільшилася на 31,1%.

Навантаження на процесор PostgreSQL також трохи зменшилося.

Показник Read IOPS був майже нульовим в обох тестах, оскільки частина даних могла читатися з пам'яті бази без звернення до диска.

## Частка влучань у кеш

Після тестування з увімкненим Redis отримано такі результати:

- Кількість влучань у кеш (Hits): 2345
- Кількість промахів (Misses): 1543
- Загальна кількість звернень до кешу: 3888
- Частка влучань у кеш: 60,31%

Частка влучань обчислюється:

2345 / 3888 × 100% = 60,31%

Це означає, що приблизно 60% запитів до списку пісень отримували дані безпосередньо з Redis, без повторного читання з PostgreSQL.

Решта запитів отримували дані з бази, після чого вони зберігалися в кеші.

## Застарілі дані після запису

Для кешування встановлено час життя даних (TTL) 60 секунд.

Це означає, що без додаткового очищення кешу клієнт може бачити застарілі дані до 60 секунд після їх зміни.

У моєму API після створення або видалення пісні кеш автоматично очищається.

Тому за нормальних умов наступний запит отримує актуальні дані з PostgreSQL, після чого оновлений список зберігається в Redis.

Якщо очищення кешу не спрацює, старі дані можуть залишатися до завершення TTL.

Щоб зменшити час відображення застарілих даних, можна:

- Зменшити TTL із 60 до 30 секунд.
- Очищати кеш після кожного запису.
- Оновлювати дані в Redis одразу після змін у PostgreSQL.
