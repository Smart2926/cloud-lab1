## Асинхронна обробка через чергу

Для реалізації асинхронної обробки операцій запису
використовувалася служба Azure Service Bus.

Було створено чергу music-tasks та окремий
контейнер ca-music-worker, який отримує повідомлення
з черги та виконує запис у PostgreSQL.

## Що змінилося для клієнта

Раніше при створенні пісні через POST /songs
клієнт очікував завершення запису в базу даних
та отримував відповідь 201 Created.

Тепер додано новий маршрут POST /songs/async.

Після надсилання запиту API створює завдання,
поміщає повідомлення в чергу та повертає
відповідь 202 Accepted.

Це означає, що запит прийнято, але операція
створення пісні ще не обов'язково завершена.

Разом із відповіддю клієнт отримує унікальний
ідентифікатор завдання job_id.

Сам запис пісні в базу даних виконує окремий Worker.

Звичайний маршрут POST /songs залишився без змін.

## Як клієнт дізнається результат

Для перевірки результату використовується
маршрут GET /jobs/{job_id}.

Клієнт передає ідентифікатор завдання та
отримує інформацію про його поточний стан.

Можливі стани завдання:
- queued — завдання очікує на обробку.
- processing — Worker виконує завдання.
- completed — пісню успішно створено.
- failed — під час обробки виникла помилка.
Після успішного завершення завдання клієнт
отримує статус completed та ідентифікатор
створеної пісні song_id.

Якщо завдання ще виконується, клієнт може
повторити запит через деякий час.

## Доставка «щонайменше один раз»

Доставка «щонайменше один раз» означає,
що кожне повідомлення може бути доставлене
обробнику один або декілька разів.

Для отримання повідомлень використовується
режим Peek-Lock.

Після отримання повідомлення Azure Service Bus
тимчасово блокує його для інших обробників.

Worker виконує операцію запису в PostgreSQL
та після успішного завершення підтверджує
обробку повідомлення.

Якщо Worker завершить роботу або виникне
помилка до підтвердження, повідомлення може
бути доставлене повторно.

Такий механізм дозволяє зменшити ризик втрати
завдань, але потребує захисту від їх
повторного виконання.

## Повторна обробка повідомлення

Кожне завдання має унікальний ідентифікатор job_id.

Перед створенням пісні Worker перевіряє
стан відповідного завдання в PostgreSQL.

Якщо завдання вже має статус completed,
повторне створення пісні не виконується.

Worker лише підтверджує отримане повідомлення,
після чого воно видаляється з черги.

Перевірка стану та створення пісні виконуються
в межах транзакції з блокуванням запису завдання.
Це дозволяє уникнути створення однакових пісень
при повторній обробці одного повідомлення.

Якщо під час обробки виникає помилка,
повідомлення може бути доставлене повторно.

Для черги встановлено максимальну кількість
спроб обробки — 5.

Якщо повідомлення не вдалося обробити після
встановленої кількості спроб, воно переміщується
до спеціальної черги помилок dead-letter queue.

Це дозволяє зберегти проблемне повідомлення
для подальшої перевірки.
